# Phase 1 Product Contract

Status: **FROZEN_V0.12**

## 1. Product goal

Job Search System 是长期本地 JD 管理与求职决策系统。
Phase 1 解决的是：持续收集 JD → 规范化 → 判断是否仍在招 → 按匹配基线筛选 → 查看详情与证据 → 选择合适简历版本。

首页必须是 **JD 列表**。
Phase 1 是 decision-support system，不是自动投递 Agent。

## 2. Core pages

Phase 1 只有三个顶层视图：
1. JD 列表（首页）
2. 简历列表
3. 个人信息（同页同时展示职业事实、匹配规则与可解释个人画像）

JD 详情不是独立页面；必须在 JD 列表中展开/收起查看。
个人信息与个人画像不得拆成两个菜单/页面；画像只能由职业事实真源与冻结规则派生，不得脱离事实源自由生成。

## 3. JD List

默认列/可见信息至少包含：岗位、公司、来源、地点、薪资、经验、学历、匹配分、学历风险、招聘状态、职位发布时间、招聘者活跃观察、最后验证时间、首次发现时间，以及 BOSS 原始详情状态。招聘者活跃必须优先展示 Provider 返回的原始可证明文本（例如“在线/离线/今日活跃”）；没有精确时间戳时不得伪造成具体活跃时间。

Phase 1 当前 live discovery 只接 BOSS 直聘；只保留上海岗位，检索优先青浦区。默认列表先展示 Provider 可证明发布时间的岗位并按 `published_at DESC` 排序；同时间粒度下青浦优先。Provider 能证明 `published_at` 时，只把最近 2 个月内的岗位标记为“已证明最近”；Provider 无法证明发布时间时，岗位仍可作为本次真实 live discovery 候选入库和展示，但 `published_at` 必须保持 `NULL`、UI 明确显示“发布时间未知”，且不得被计入“已证明最近 2 个月”集合。

默认生产/本地运行时的 JD 列表不得自动注入 synthetic/demo jobs。Provider、匹配 baseline/terms、resume metadata 等 reference bootstrap 可以在空库初始化时建立，但 demo job fixtures 必须与 reference bootstrap 分离；只有显式 test/demo 模式才允许注入 synthetic jobs，且它们不得参与真实 live 统计或验收。

默认候选列表只展示目标技术岗位，并隐藏不适合作为当前求职候选的岗位：标题或经验字段表明实习、校招、应届、在校/应届、管培、毕业生/校园招聘（含明确届次校招标题），以及标题表明明显领导/管理/过高职级（负责人、总监、主管、经理、首席、架构师、专家、Leader/Head）。这些岗位仍保留在 SQLite 作为采集历史，不做物理删除；用户明确要求查看原始全集时才允许解除默认隐藏。

筛选必须支持：关键词、公司、Provider、城市/区域、薪资、经验、学历、职位方向、匹配区间、学历风险、招聘状态、首次发现时间、最后验证时间，以及“只看新增 / 只看未查看 / 只看确认在招”。
列表必须支持组合筛选、排序和分页。

列表默认优先回答两个问题：
1. 这个岗位适不适合？
2. 这个岗位现在还在不在招？

## 4. JD Inline Detail

列表展开详情必须包含四个区域：
- 原始 JD：title/company/salary/location/experience/education/full JD/recruiter/source URL。
- 规范化信息：role_family、seniority、技能、职责、bonus、薪资结构。
- 匹配解释：命中词、风险词、缺口、学历风险、rule_score。
- 招聘真实性：当前状态、可信度、最后验证时间、验证方法、证据及历史 timeline。

同时能够查看 JD snapshot timeline；当前数据不能覆盖历史证据。展开/收起不得导航到独立 JD 详情页。

## 5. Resume List

管理事实母版以及 AI研发效能/Coding Agent、资深前端/云平台、AI全栈/Agent应用和后续定向版本。
仓库根级 `career-assets/` 是当前职业资产入口，其中 `career-assets/职业事实.md` 是唯一活动职业事实真源；本系统只保存简历版本快照、content hash、方向、状态、source path 及可展示内容。项目核验材料与源码跟随 `career-assets/项目/<project>/`；已吸收且不再承担核验责任的旧资料/派生产物不长期保留。

## 6. Personal Info and Profile

“个人信息”是唯一顶层页面：同页管理/展示职业事实、baseline 与 term/rule，并展示从事实与规则派生的目标方向、能力、偏好与风险解释。v0.10 Repository Cognitive Load Reduction 后，唯一活动职业事实真源固定为：
- `career-assets/职业事实.md`

职业事实治理为 `career-assets/事实治理.md`，证据索引为 `career-assets/证据/索引.md`，派生画像为 `career-assets/定位/候选人画像.md`。绩效、个人 Git、ONES 与完整项目源码按项目归档；旧混合事实、旧规划/学习资料、自动聚合报告和历史 handoff 在 canonical 吸收后删除。Evidence 只能约束/证明事实，不能反向创造事实。

管理 baseline 与 term/rule。`match_type` 固定为：
`STRONG_BOOST / BOOST / INCLUDE / RISK / STRONG_RISK / EXCLUDE`。
Baseline 必须有方向、说明、启用状态；term 必须有词、类型、分类、权重、备注和启用状态。

## 7. Explicitly out of scope

Phase 1 不实现：
- 投递页面、自动打招呼、自动投递。
- 任何浏览器写操作。
- MCP / Playwright Chrome 的真实投递执行。
- PostgreSQL、Redis、Elasticsearch、Docker 或重 ORM 作为基础依赖。
- 把 Provider 特有逻辑写进核心 Domain/UI 合同。
- 在业务数据库保存 cookie、token、security_id、验证码答案或账号凭证。

Phase 1 的 BOSS live discovery/detail 以 `boss-agent-cli` 公共 CLI 为唯一正常入口；系统不得因为单次 CLI 超时或内部 transport 异常就改走外部 Playwright/Codex Chrome 页面控制。CLI 内部如何选择 Bridge/CDP/Patchright 属于 CLI 自身实现细节，Job Search System 只依赖其公共只读命令与结构化输出。已验证的无 `chrome.debugger` Chrome Extension 不进入 Phase 1 搜索/详情主链路，保留给后续投递/浏览器写操作阶段；未来写操作必须另行升级 SDD，并在真实外部动作完成后才能引入 application record。

## 8. Primary acceptance journey

`打开系统 → JD 列表 → 默认只看当前目标技术候选（排除应届/实习/校招/管培/明显领导岗）→ 能识别“发布时间未知”的实时发现候选 → 展开某个 JD → 看匹配原因 → 看学历风险 → 看 Provider 招聘者活跃观察/是否仍在招 → 看验证历史/快照 → 来源 URL 可用时打开 BOSS 原始详情 → 看推荐简历 → 在个人信息页同时看事实、规则与个人画像`。

任何实现如果无法完成上述旅程、把 JD 详情重新做成独立页面、或把个人画像重新拆成独立顶层视图，都视为偏离本合同。
