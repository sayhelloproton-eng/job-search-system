# Phase 1 System Design

Status: **FROZEN_V0.12**

## 1. Runtime shape

Phase 1 是单用户、本地优先应用。
基线运行时：Node.js 24 + TypeScript；SQLite 通过 `node:sqlite` 访问。
核心系统启动不得依赖 PostgreSQL、Redis、Elasticsearch、Docker、托管数据库或模型 API。

### SDD Design Decision D-005 — local boundary

默认只监听本机 loopback（例如 `127.0.0.1`）；不以公网服务作为 Phase 1 前提。
数据库默认路径为 `app/db/runtime/job-search.db`，本地资产通过明确 path/hash 引用。
UI framework、样式库和构建器属于实现选择，只要不改变 SDD 合同即可后置决定。

## 2. Component boundaries

1. **Domain**：JD identity、verification state、education risk、matching 规则与不变量。
2. **Application**：列表/详情、ingestion、verification、resume、baseline、evaluation、search-run 用例。
3. **Persistence**：SQLite repositories、transaction、migration。
4. **Provider adapters**：discovery/detail/normalization/verification evidence。
5. **Presentation**：三个 Phase 1 顶层视图（JD 列表 / 简历列表 / 个人信息），只消费 Application contract；个人画像并入个人信息。
6. **Local asset store**：简历 snapshot 与清洗后的大体积 evidence 文件。

Domain 不依赖 Provider/browser；Presentation 不自行抓页面并判断招聘真实性；Persistence 不包含业务打分规则。

## 3. Provider contract

BOSS、猎聘、智联、51Job、公司官网都只是 Provider。
Provider 允许负责：
- discovery：发现职位候选。
- detail：读取职位详情。
- normalization：把源字段转换为统一 candidate。
- verification evidence：返回可验证观察与清洗后的证据。

Provider 不允许负责：
- 决定教育 Hard Block。
- 决定匹配分公式/UI 排序策略。
- 改写简历职业事实。
- 把 CAPTCHA/风控推断成 CLOSED。
- 在 Phase 1 执行打招呼、投递或任何浏览器写操作。

统一 Provider 输出至少区分：source identity、normalized candidate、verification observation、sanitized evidence、provider error/blocked reason。
Provider adapter 失败不能破坏已有 JD 历史。

### SDD Design Decision D-007 — BOSS CLI-first provider boundary

Phase 1 当前唯一 live Provider 为 BOSS。Job Search System 必须通过已安装的 `boss-agent-cli` 公共 CLI 完成 BOSS discovery/detail；正常入口是 `boss search ...` 与 `boss detail ...` 的结构化输出，而不是由本系统直接接管 BOSS 页面。

Provider Adapter 负责：构造受控 CLI 参数、启动短生命周期子进程、设置明确 timeout、解析 JSON、清洗 `security_id`/token/cookie 等秘密、规范化职位字段并把 CLI 失败映射为 Provider error。单次 CLI 超时/transport 异常不得自动切换到外部 Playwright、Codex Chrome 或自建页面抓取链路。

`boss-agent-cli` 内部如何选择 Bridge/CDP/Patchright 属于第三方 CLI 的实现细节，不进入 Job Search System 的 Provider contract；系统只依赖其公共命令和可观察结果。2026-08-22 已在本机以 `boss-agent-cli 1.18.0` 实机搜索上海 `AI Agent`，返回 15 个真实岗位且 `has_more=true`，因此 CLI-first 路线已有真实能力证据。

此前验证通过的无 `chrome.debugger` Chrome Extension 保留为**后续投递/浏览器写操作阶段**的 BOSS 专用执行候选，不作为 Phase 1 discovery/detail 实现或验收前提。Phase 1 仍禁止打招呼、投递、发送简历、收藏、沟通或其它站点写操作。

### SDD Design Decision D-008 — public CLI field-gap handling

`boss-agent-cli 1.18.0` 的公共 `search/detail` DTO 已确认不暴露职位发布时间和原始职位 URL。Job Search System 不得穿透 CLI 去依赖第三方内部 `jobList/jobInfo` 原始结构，也不得根据 `job_id` 猜测 URL。真实上海 live search 返回且具稳定 source identity 的岗位，即使 `published_at/source_url` 缺失，也允许作为实时发现候选进入 current projection；缺失值保持 `NULL` 并写入 sanitized search-run evidence。只有可证明 `published_at` 的岗位才能进入“已证明最近 2 个月”集合。

该字段缺口不改变招聘真实性状态机：岗位本次确实出现在搜索列表时可记录 `LISTED`；“发布时间未知”不是 `BLOCKED` 招聘状态。默认列表必须将已知发布时间的岗位排在未知发布时间候选之前。

### SDD Design Decision D-009 — reference bootstrap 与 demo fixtures 分离

默认生产/本地运行时不得因为空库而自动插入 synthetic/demo jobs。空库启动允许初始化运行所需的 reference bootstrap（例如 Provider registry、active match baseline/terms、resume metadata），但这些 reference records 必须与 demo job fixtures 使用独立入口。

Demo jobs 只能在显式 test/demo 选项下创建；默认 `createApp()` / `npm start` 不得启用 demo job injection。Synthetic jobs 不得进入真实 live 统计、真实求职 shortlist 或 Phase 1 live acceptance。该决策不改变现有 SQLite schema，只改变 bootstrap/fixture 生命周期边界。

### SDD Design Decision D-010 — candidate projection 与 personal view 收口

默认 JD API/UI 使用多路线候选 projection：第一层目标信号覆盖 AI Agent/智能体/大模型/LLM，以及高级前端/资深前端、前端偏全栈/全栈、研发效能、FDE；第二层仍要求标题具开发/研发/工程师/全栈/前端/后端/算法/平台/FDE 等技术信号。默认继续隐藏标题或经验字段表明实习/校招/应届/在校应届/管培/毕业生/校园招聘（含明确届次校招）的岗位，以及标题表明负责人/总监/主管/经理/首席/架构师/专家/Leader/Head 等明显领导或过高职级岗位；原始采集记录继续留在 SQLite，不物理删除。该调整用于与当前 `AI Agent / 高级前端-前端偏全栈 / FDE` 三条求职与面试 Route 对齐。

个人信息与个人画像合并为一个 Presentation 顶层视图；现有 `/api/personal-info` 与 `/api/personal-profile` 可继续作为内部 read model，但 UI 必须在同一页面组合展示。招聘者活跃展示优先使用 `jobs.recruiter_activity` 的 Provider 原始文本；`recruiter_recently_active` 只能作为结构化辅助，不能在原始文本存在时把状态降级成“未知”。

## 4. Ingestion workflow

`Provider result → normalize → resolve logical identity → upsert current job → compare material hash → optional snapshot → update search_run counts`。

### SDD Design Decision D-006 — transactional write units

单个逻辑岗位的 identity resolve、current projection 更新与可选 snapshot 写入必须在同一事务中完成。
单次 verification 必须先新增 history row，再在同一事务更新 `jobs.current_verification_status/last_verified_at`。
失败时不得留下“projection 已变但 history 没写”或相反的半状态。

## 5. Verification workflow

`request verification → Provider observation → Domain classify status → append job_verifications → update current projection`。
Domain classification 必须执行 `BLOCKED != CLOSED` 规则；Provider 原始状态字符串不能直接写进冻结枚举。

## 6. Match evaluation workflow

`load active baseline + active terms → normalize searchable JD text → deterministic term matching → calculate rule_score/excluded/final_score → persist explanation + evaluator_version`。
Baseline/term 变化后允许重新评估；新结果必须带新 `evaluated_at`，不允许静默失去算法/规则变更痕迹。

## 7. Resume workflow

v0.12 后，Personal Info/Profile 只从 `career-assets/职业事实.md` 读取活动职业事实；项目核验材料都位于 `career-assets/项目/<project>/`，但仍不进入 runtime source list。历史简历继续从 `career-assets/简历/历史/` 读取，且不得反向成为事实真源。
导入时计算 content hash、记录仓库内 source path，并可生成本地 snapshot path。Reference bootstrap 写入的 resume `source_path` 必须解析到真实存在的 `career-assets/` canonical 文件或 `career-assets/简历/历史/`。
系统允许展示/选择版本，但任何简历、画像、JD 或 AI 推断都不得反写/覆盖 `career-assets/职业事实.md`；事实更新必须经过 evidence/provenance 裁决。完整项目源码与项目级绩效/Git/ONES 只在对应 `career-assets/项目/<project>/` 内按需核验，不作为默认模型上下文。

## 8. Read model

JD List 查询必须能在 SQLite 层完成主要组合筛选、候选 projection、排序、分页；不能先全表加载到内存再过滤。默认 projection 在 SQL 层保留目标技术岗位并隐藏 D-010 的应届/实习/校招/管培与领导/过高职级标题；`scope=all` 可用于显式诊断原始采集全集。默认排序先按 `published_at IS NULL ASC`，再按 `published_at DESC`；同时间粒度下青浦优先，确保发布时间未知的实时候选不会排在已证明时间的岗位之前。
JD List read model 必须返回 `recruiter_activity` 原始文本以及可选结构化活跃字段；Presentation 优先展示原始文本。JD Inline Detail 通过 job id 聚合 current job、snapshots、verifications、latest match result 与推荐/相关 resume metadata，并作为列表行展开数据返回；Presentation 不创建独立详情页。

## 9. Error semantics

Provider/browser-related blockage属于外部 observation error；核心应用必须仍可读取已有本地数据。
单个 Provider 失败不能阻止其他 Provider 的已有数据浏览。
缺失本地 resume/evidence 文件应显示“资源不可用”，不能悄悄生成替代内容。

## 10. Security boundary

Provider adapter 在 evidence 进入 Domain/Persistence 之前负责 secret redaction。
业务日志同样不得输出 cookie/token/security_id 等敏感值。
Phase 1 不实现账号系统，也不把浏览器登录态复制进 SQLite。

## 11. Provider rollout order

Phase 1 当前只实现 BOSS live Provider；猎聘、智联、51Job、公司官网保留为后续 Provider 扩展，不进入本轮 live discovery 验收。
Domain、SQLite 与四个顶层视图仍不得依赖 BOSS 在线才能启动和读取已有本地数据；Phase 1 的真实职位验收必须使用 BOSS 上海真实 live search 结果，不能以少量 seed 记录替代。Provider 能证明 `published_at` 的结果必须满足最近 2 个月；Provider 当前无法证明发布时间的结果可以作为“发布时间未知”的实时发现候选验收，但不得冒充已证明最近。

## 12. Architecture acceptance

只要替换 Provider adapter，核心 JD identity、verification、education risk、matching、resume 和 UI contract 不应变化。
如果新增 Provider 必须修改核心状态枚举或页面业务语义，说明 Provider 解耦失败。
