# Phase 1 Domain Rules

Status: **FROZEN_V0.5**

## 1. Recruitment verification

招聘真实性必须独立建模；“发现了 JD”不能等价为“仍在招聘”。

固定状态：
- `NEW`：刚发现，尚未验证。
- `LISTED`：仍出现在 Provider 搜索列表，但未完成详情级 live 证明。
- `LIVE_CONFIRMED`：详情存在、无关闭信号，且沟通/投递入口仍可用。
- `RECRUITER_CONFIRMED`：招聘者明确确认仍在招。
- `UNKNOWN`：证据不足，无法得出更强结论。
- `BLOCKED`：验证码、security_check、风控、登录异常等阻断验证。
- `STALE`：超过复验窗口或历史导入，当前 live 状态已不可信。
- `CLOSED`：存在明确下线、关闭或招聘结束证据。

核心不变量：`BLOCKED != CLOSED`。
任何 security_check / CAPTCHA / 登录异常 / 风控都不得推断为 `CLOSED`。
UI 必须使用中文展示这些状态，但持久化/Domain 枚举保持英文稳定值；中文文案不得反向成为状态真值。

每次验证都新增 `job_verifications`；历史只追加，不覆盖。
`jobs.current_verification_status` 只是最新 projection，不是真实历史本身。

## 2. Education risk

学历要求不能直接等价为 Hard Block。

- `LOW`：学历不限 / 大专 / 未明确。
- `MEDIUM`：普通本科、本科+3年、本科+5年、本科+5-10年；必须正常展示。
- `HIGH`：明确统招本科、全日制本科、第一学历本科、985/211、明确硬性本科要求。
- `VERY_HIGH`：硕士、博士、特定高学位或院校硬约束。

学历风险与匹配排除独立：任何学历文本都不会自动生成 `EXCLUDE`。
高风险岗位默认仍入库、仍展示、可筛选；风险必须附带中文解释文本。
默认求职偏好为大专/本科；硕士/博士岗位降低匹配优先级，但不得因学历要求自动 `EXCLUDE`。该偏好应通过 Personal Info 中的 baseline/rule 明确表达并保留解释。

## 3. Match baseline

固定 `match_type`：`STRONG_BOOST / BOOST / INCLUDE / RISK / STRONG_RISK / EXCLUDE`。
每个 term 只属于一个 baseline，并保存 category、weight、notes、active state。
Phase 1 只要求确定性 `rule_score`；不依赖语义模型。
`semantic_score` 仅作为未来扩展的 nullable 字段，不参与 Phase 1 结果。

每次评估必须保留：命中词、风险词、排除词、最终解释及 evaluator version。
同一个 job + baseline 在同一 evaluator version 下，对同一输入必须得到相同结果。

### SDD Design Decision D-003 — Phase 1 rule score

Planning Kit 未指定数学公式；v0.1 为了让测试可执行，冻结以下算法：
- 未命中任何 term 时，`rule_score = 50`（中性基线）。
- `STRONG_BOOST / BOOST / INCLUDE` 命中时增加 `abs(weight)`。
- `RISK / STRONG_RISK` 命中时减少 `abs(weight)`。
- `rule_score = clamp(50 + contributions, 0, 100)`。
- 任一 active `EXCLUDE` 命中：`excluded = true` 且 `final_score = 0`。
- 未命中 `EXCLUDE`：`final_score = rule_score`。

`EXCLUDE` 只影响该 baseline 的评估结果，不删除、不隐藏数据库中的 JD；用户仍可通过详情查看。

## 4. Job identity

优先身份：`provider_id + external_job_id`。
当 Provider 无 external id 时使用 deterministic `identity_fingerprint`。

### SDD Design Decision D-002 — fallback fingerprint

1. 有 canonicalized source URL：`sha256(provider_code + canonical_url)`。
2. 无稳定 URL：`sha256(provider_code + normalized_company + normalized_title + normalized_city + normalized_district)`。

URL canonicalization 必须移除 tracking/query noise，但不得移除会改变职位身份的 path/job id。

重复 discovery 只更新同一逻辑岗位的 `last_seen_at`；不得无限新增 jobs。
只有 material content 变化才新增 snapshot；相同 `content_hash` 不重复插入。

## 5. Historical import

Planning Kit 要求历史 JD 不得冒充 current live。

### SDD Design Decision D-004 — origin kind

`jobs.origin_kind` 固定为：
- `LIVE_DISCOVERY`
- `HISTORICAL_IMPORT`

历史导入默认 `current_verification_status = STALE`；除非后续产生新的真实 verification evidence，否则 UI 不能将其展示为 `LIVE_CONFIRMED` / `RECRUITER_CONFIRMED`。

## 6. Snapshot semantics

Snapshot 是职位内容历史，不是验证历史。
用于判断 material change 的 hash 输入至少包含：title、company、salary text、experience text、education text、location text、JD text、recruiter activity text。
验证状态变化只写 `job_verifications`，不会为了状态变化单独制造 JD snapshot。

## 7. Evidence rule

Provider 返回“无法访问”只能形成验证 evidence；不能被 Domain 解释成关闭。
所有当前状态都必须能够追溯到最新一条有效 verification，`NEW`/`STALE` 除外。

## 8. Phase 1 discovery scope

Phase 1 live discovery 当前固定为 BOSS 直聘。候选岗位必须满足：
- 城市为上海；非上海结果不得进入 live discovery projection。
- 检索优先青浦；已知 `published_at` 的岗位默认按 `published_at DESC`，同时间粒度时青浦优先；`published_at IS NULL` 的实时发现候选排在已知时间之后。
- `published_at` 可确定时，只把当前时间向前 2 个月内发布的岗位纳入“已证明最近”集合；明确早于 2 个月的岗位拒绝进入 live projection。
- Provider 无法可靠给出发布时间时，不得伪造时间。若该岗位由本次真实 BOSS live search 返回、城市为上海且具有稳定 source identity，则允许以 `published_at = NULL` 的实时发现候选入库，并在 search-run evidence 中记录 `PUBLISHED_AT_MISSING`；它可以因本次搜索列表观察获得 `LISTED`，但不得被宣称为“已证明最近 2 个月”。
- `published_at` 缺失是“发布时间证据不足”，不等价于招聘真实性 `BLOCKED`；招聘状态仍只由招聘验证证据决定。

招聘者“最近活跃”是 Provider observation，不等价于 `LIVE_CONFIRMED`；它可以辅助展示与验证，但不能单独把岗位提升为更强招聘真实性状态。
