# Phase 1 Change Governance — IRON LAW

Status: **FROZEN_V0.2**

## 1. 铁律

任何已经讨论并形成确定结论的产品、领域、数据、接口、流程、验收或外部可观察行为，在修改生产实现之前，必须严格遵守：

`Decision → SDD update/version → Test Plan update → TDD RED → Implementation → GREEN → Browser/Acceptance Verify`

这是 Job Search System 的项目级硬门，不是建议流程。

禁止：
- 先改代码，再补 SDD；
- 先改实现，再修改测试去适配实现；
- 跳过 Test Plan 直接写业务代码；
- 没有看到预期 RED 就宣称完成 TDD；
- 确定性需求只停留在聊天记录中而不进入 SDD。

## 2. 什么算“确定性变更”

以下事项一旦在讨论中明确决定，就必须先进入 SDD：
- 页面、字段、筛选、排序、交互和用户旅程；
- Domain 状态、风险等级、匹配、去重、历史规则；
- SQLite Schema、migration、约束、索引、数据所有权；
- API contract、事务语义、错误语义；
- Provider 边界、能力、采集与验证规则；
- 安全边界、运行方式、验收标准；
- 任何会改变用户或外部系统可观察行为的技术设计。

如果只是探索、调研、临时实验或尚未定案的方案，可以不立即升版 SDD；一旦结论确定，进入实现前必须补齐本流程。

## 3. 强制执行顺序

1. 把确定结论写入对应 SDD，并升版本/记录变更。
2. 更新 requirement → test case 追踪与 Test Plan。
3. 新增或修改 TDD 测试，先证明出现预期 RED。
4. 只做让该批测试通过所需的最小实现。
5. 跑 GREEN，并执行受影响的 regression。
6. 对页面/浏览器行为做真实 Browser/Acceptance Verify。

## 4. Gate semantics

任一确定性变更只有在以下状态同时成立时才允许进入实现：

- `SDD_UPDATED = YES`
- `TEST_PLAN_UPDATED = YES`
- `TDD_RED_OBSERVED = YES`

实现完成后必须达到：

- `TDD_GREEN = YES`
- `REGRESSION_PASS = YES`
- 对 UI/浏览器行为：`BROWSER_ACCEPTANCE_PASS = YES`

只要前三个前置门有一个为 NO，就必须停止生产实现修改。

## 5. Authority

本文件是 `docs/系统规范/*` 的项目级变更治理真源，与具体产品/Domain/Data/System SDD 同级生效。
后续任何 Chat、Codex、Agent 或人工开发都必须遵守；聊天中的即时指令不能绕过此铁律，除非先明确修改本治理 SDD 本身。
