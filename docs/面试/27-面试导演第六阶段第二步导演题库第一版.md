## 1. Corpus 只回答什么

Question Corpus 回答“可能问什么”；Director Corpus 只回答：

```text
这一轮为什么存在
谁通常负责判断
常见时长 / 阶段结构
重点 Competency / Signal
真实追问如何从上一答继续
什么时候通常切 Coding / Design / Case
什么只是单篇观察，不能泛化
```

P6-2 不新增正式题，不修改 Scene/Signal Authority，不产生 company-specific 硬编码。

## 2. Evidence Grade

- `OFFICIAL`：招聘方/结构化招聘官方资料，可决定方法与公开流程事实；
- `MULTI_REPORT`：至少两份相互独立的近期真实记录出现同一过程 Pattern；
- `SINGLE_REPORT`：单篇真实面经，只做 observation；
- `INFERRED`：由 Route/JD/多类证据推导的默认模拟结构，必须显式标记。

优先级：`OFFICIAL > MULTI_REPORT > SINGLE_REPORT > INFERRED`。低等级证据不能覆盖高等级证据。

## 4. OFFICIAL 方法约束

从 OPM / Greenhouse / Amazon 只吸收稳定的招聘过程原则：

1. Interview Focus 必须来自岗位关键 Competency，不从题库反推岗位标准；
2. 同一 Round 的评价标准事先确定，不能随候选人表现改变；
3. Probe 可以存在，但语义必须服务于当前 Competency / Evidence；
4. Scorecard 要记录可观察 Evidence，而不是“我感觉不错”；
5. 一个 Interview Loop 可以让不同 Interviewer 分工评估不同技术/非技术能力；
6. 时长和 Competency 数量要匹配，不能无限扩展；
7. System Design / Coding 等 work-sample 类任务应观察澄清、推理和验证过程，而不只看最终答案。

Amazon 的 `4 × 55min` 只作为“真实公司会明确分轮和时间盒”的强例，不作为三条 Route 的固定轮次数量。

OPM 高结构化要求“相同 predetermined questions/order”比我们的训练 Director 更严格；本系统不照搬为死题单，而是保留它的 **固定 Competency + 固定评分尺 + 受控 Probe**，再用 Director 做自适应取证。

## 5. 跨路线 Reality Pattern

近期真实面经反复出现：

```text
自我介绍 / 项目锚点
→ 从候选人主动说出的关键词开始下钻
→ 验证本人贡献 / 实现 / Failure / 指标真实性
→ 切岗位专项技术
→ Coding / Design / Case（按岗位和轮次）
→ 反问
```

所以默认 Director 不应把题库按主题目录顺序朗读；项目回答本身会形成下一轮 Probe 的高价值上下文。
## 6. AI Agent / Developer Tools Pattern

Evidence：2026 Q2/Q3 多份字节、淘天、拼多多、AI 应用面经。

稳定重复 Pattern：
- 开场快速建立 AI/Agent 项目主线；
- 大量问题直接从项目中的 Agent 架构、RAG、Tool/MCP、Context、Eval、模型选择向下追；
- 面试官常问“为什么这样做 / 怎么评估 / 出错怎么定位 / 为什么不用另一种”；
- Coding、数据结构、数据库/网络/后端基础仍可能插入，AI 岗不等于只问 LLM；
- 二面更容易从“会不会”转向“方法论、评测、优化、场景设计、约束变化”。

导演默认推断：

```text
Tech1: PROJECT_ANCHOR → AGENT_IMPLEMENTATION → ENGINEERING_BASELINE → CODING → Q&A
Tech2: PROJECT_DEEP_DIVE → EVAL/RELIABILITY → ARCH/JUDGMENT → SCENARIO/DESIGN → Q&A
HM:    SCOPE/OWNERSHIP → VALUE/ADOPTION → FAILURE → FUTURE_TRANSFERABILITY → Q&A
```

Exact phase budget 属 `INFERRED`，不是公司事实。

## 7. 高级前端 / 前端偏全栈 Pattern

2026 近期面经仍保留 React/Vue、Browser、Promise、缓存、性能、工程化和 Coding，但已经明显出现 SSE/API、DB、Node/FastAPI、Agent/RAG/AI Coding 等跨栈问题。

高级候选人的 Reality 不应退化为“基础八股升级版”：项目复杂度、性能因果链、工程边界、迁移、Node/服务端责任、系统设计和 AI 工程迁移性应占更高权重。
默认 Pattern：

```text
Tech1: INTRO → PROJECT → FE_BASELINE → CODING → ENGINEERING → Q&A
Tech2: PROJECT_DEEP_DIVE → ARCH/PERF → FULLSTACK_BOUNDARY → SYSTEM_DESIGN → Q&A
HM:    SCOPE/OWNERSHIP → PLATFORM_VALUE → CROSS_TEAM → FAILURE/JUDGMENT → Q&A
```

2026 有经验前端的社区总结把项目、Coding、核心原理、System Design、AI 都列为现实组成部分；比例只能当 SINGLE_REPORT observation，不能写成统一权重。

## 8. ToB / FDE Pattern

FDE 的最大现实特征不是某个框架，而是**技术 + 客户 + 模糊需求 + 可验收交付**同时被观察。

近期社招完整记录显示：

```text
HR 基础约束
→ Tech1 项目 / 排障 / 客户本地环境 / 独立拆需求 + Coding
→ Tech2 客户沟通 + 现场流程 Agent 化 Case + Skill/Tool/Prompt/Eval/HITL
→ Leader 项目 + 超预期贡献 + 难客户 + Context/Memory/RAG 深挖
→ HR / Offer
```

这是 `SINGLE_REPORT` 的强 observation，不得写成“字节 FDE 固定流程”。但多个 FDE 求职/岗位样本共同支持以下 Competency：需求澄清、方案/架构、系统集成、代码落地、客户沟通、排障、部署、评测、验收、产品化沉淀。

因此默认子型继续分：
- `FDE_ENGINEERING`：技术实现、系统集成、可靠性权重大；
- `FDE_SOLUTION`：业务澄清、架构、取舍与客户沟通权重大；
- `FDE_DELIVERY`：现场排障、部署、验收、风险权重大；
- `FDE_PRODUCTIZATION`：从重复交付抽象 Skill/Tool/平台能力权重大。

## 10. InterviewerArchetype Reality V1

- `ENGINEER_SCREEN`：先验证下限和真实性；喜欢问实现、Debug、边界、验证；不会因“高级候选人”跳过基本工程能力。
- `SENIOR_STAFF_TECH`：重点验证复杂度、Trade-off、Failure、Architecture Restart、系统边界和上限；强回答后会换约束而非重复八股。
- `HIRING_MANAGER`：把过去事实映射到未来可托付 Scope；关心 Ownership、Value、跨团队推进和失败后的恢复能力。
- `FDE_BUSINESS_ENGINEER`：从客户目标和未知信息出发，验证 decomposition、技术方案、沟通、交付风险与验收闭环。
- `RECRUITER`：验证固定事实、动机、地点/到岗/薪资等约束与交易风险，不承担技术深度评分。
## 11. Freshness / Dedupe / Conflict

Freshness：
- `OFFICIAL`：每次进入 company override 或方法改版前重新验证；常规 180 天检查一次；
- `MULTI_REPORT`：要求至少 2 个独立来源，主样本尽量在 180 天内；
- `SINGLE_REPORT`：120 天后不再作为 current pattern，只保留历史 observation；
- `INFERRED`：只要上游 JD/Route/高等级 Pattern 变化就重新计算。

去重键：`company + normalizedRole + roundType + interviewDate + author/source`；聚合帖若复制多篇原帖，不计作额外独立来源。

冲突处理：
1. 官方流程和社区记录冲突：官方定义流程真源，社区记录保留实际变形；
2. 同公司不同团队/岗位冲突：先拆 team/role，不做平均；
3. 同岗位不同轮次冲突：按 Round 分开；
4. 两份独立近期面经重复出现才升级为 `MULTI_REPORT`；
5. 无法消解时保留多个 Pattern，并降低 company-specific confidence。

## 12. Company Override Gate

只有以下任一条件满足，才允许覆盖 Route Default：
- 官方 Hiring Guide 明确给出该 Role/Level 的 Loop；
- 同公司同类岗位至少 2 个独立近期报告形成相同 Round Pattern；
- 用户本人完成真实面试后，用该次事实覆盖“这次面试”的 Session Plan，但不自动泛化公司全局。

单篇面经只能改变 Probe 候选或增加 observation，不能把默认 55/60 分钟、轮数、必考题写成公司事实。
