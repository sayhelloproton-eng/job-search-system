# 03｜Python / FastAPI 第二服务端路径

## JD 为什么问

17 条有效 JD 中 14 条在任职要求里出现 Python/FastAPI 或 Python 服务端能力。目标不是把职业历史改写成 Python 后端，而是让面试官相信你能真正承担 AI 应用服务，而不是只会前端调用模型 API。

## 面试需要达到的深度

```text
Request
  ↓ validation
FastAPI endpoint
  ↓ dependency / auth / config
Service layer
  ↓ async I/O
Model / Retrieval / DB / external API
  ↓
Typed response / structured error
  ↓
Test + logs + timeout
```

需要会读、改、写一个小型生产式服务：typed schema、async、dependency、exception、timeout、test、config、health；不要求短期变成 Python 语言专家。

## Python 面试最小知识

- typing：`list[str]`、`dict[str, X]`、`Optional`/union、dataclass/Pydantic model 的用途。
- module/package：不要把所有 endpoint/service/db 逻辑写一个文件。
- sync vs async：CPU 密集不会因为 `async` 变快；async 主要提高大量 I/O 等待时的并发利用率。
- exception：业务错误、依赖错误、上游 timeout、内部 bug 需要不同语义。
- context/resource cleanup：DB/session/client 等资源必须有明确生命周期。

## FastAPI 必懂

- Request/Response model：用类型做验证和 OpenAPI contract。
- Dependency Injection：把 auth、DB session、config、service 等依赖从 endpoint 解耦。
- `async def`：适合 await 异步 DB/HTTP/model 调用；同步库仍要理解阻塞风险。
- Exception Handler：不要所有异常都吞成 200 或统一 500。
- Lifespan：初始化/释放客户端、连接池等长生命周期资源。
- Testing：普通 API 用 `TestClient`；需要异步 DB/调用链时用 async test + HTTPX/AnyIO。

## Node ↔ Python 怎么分工

短期最合理不是“全改 Python”：Node/TS 继续承担产品 API/BFF、前端契约、SSE 事件聚合；Python service 承担 retrieval、模型生态、数据/AI 组件。是否拆服务由部署、团队边界、扩缩容、依赖隔离决定，不能只因为 Python AI 库多就强拆微服务。
## 高频面试题与答案骨架

**Q1：什么时候用 `async def`？** 当调用链主要等待异步 HTTP/DB/model I/O 时；如果内部是 CPU 密集或调用阻塞库，单纯加 async 不会提升吞吐，反而要考虑线程池/任务队列/独立 worker。

**Q2：Dependency Injection 有什么价值？** 把 endpoint 与 auth/DB/config/service 生命周期解耦，便于复用、测试替换和资源管理；不是为了“写法高级”。

**Q3：模型上游超时该返回什么？** 区分客户端参数错、未授权、资源不存在、上游超时/不可用、内部 bug。对外给稳定 error code/message，对内记录 cause/correlation id；是否 retry 由错误类型和预算决定。

**Q4：Node 和 Python 为什么不合成一个服务？** 先看边界。若同团队同部署且规模小，单服务更简单；如果 AI 依赖、扩缩容、运行时、团队 ownership 明显不同，拆服务更合理。服务拆分要用复杂度换明确收益。

**Q5：如何测试 FastAPI AI endpoint？** 至少覆盖 schema validation、正常结果、upstream timeout、dependency failure、auth failure；模型/外部服务用 fake/mock，集成测试再验证真实 contract。异步资源要避免 event-loop 生命周期错误。

## 故障题

场景：FastAPI `/retrieve` 平时 100ms，突然变 8s。排查顺序：request/correlation id → 应用自身 CPU/queue → DB/vector store → embedding/rerank/model upstream → connection pool/timeout → downstream retries。不能只“加 timeout”；要定位 latency budget 在哪一层消耗。

## 最小代码能力验收

面试前至少自己写过：
1. Pydantic request/response；
2. auth/config dependency；
3. async HTTP client + timeout；
4. domain exception → HTTP error mapping；
5. pytest/TestClient；
6. async integration test；
7. `/health` 与 `/ready`。
