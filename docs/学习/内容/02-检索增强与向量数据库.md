# 02｜RAG / Retrieval / Vector DB

## JD 为什么问

17 条有效 JD 中，RAG/检索/向量在 REQ_GATE 侧约 59%，同时出现在 AI 应用、Coding Agent、知识库、ToB 交付岗位。它是当前最明确的技术 GAP。

## 最小链路

```text
Documents → parse → chunk → metadata
                    ↓
                 embed
                    ↓
              vector index
                    ↑
User Query → rewrite/embed → retrieve top-k
                              ↓
                    filter / hybrid / rerank
                              ↓
                         final context
                              ↓
                             LLM
                              ↓
                    grounded answer + citations
```

RAG 的核心不是“向量库 + LLM”，而是**把外部知识在回答时检索进 Context，并能评估检索是否正确**。

## 必懂概念

- Embedding：把文本映射到向量空间，近似表达语义相关性；相似不等于事实正确。
- Chunk：索引最小单位。过大引入噪声，过小丢失上下文；必须结合文档结构。
- Top-k：召回候选数量；k 太小漏答案，太大增加噪声、token 和 rerank 成本。
- Metadata：tenant、project、version、doc_type、ACL 等结构信息，不能全靠 embedding 表达。
- Dense retrieval：语义向量检索；对同义表达强，但精确 token/编号可能弱。
- Sparse/keyword：BM25 等词项匹配；对代码符号、错误码、产品名、版本号常有优势。
- Hybrid：组合 dense + sparse，改善单一路径失效。
- Rerank：对召回候选做更昂贵的二次相关性排序。
- Grounding：答案必须由检索证据支持；没有证据应拒答或声明不确定。

## Agentic RAG / Agentic Retrieval

固定 RAG 通常是一条预定义链：query → retrieve → rerank → context → answer。Agentic RAG 则把“是否需要继续检索、如何拆查询、是否换查询/来源”变成受控的运行时决策。

Microsoft Azure AI Search 的 agentic retrieval 是一个具体实现：对复杂请求做 query planning，拆成多个 focused subquery，并行执行 keyword/vector/hybrid retrieval，再 semantic rerank、合并结果并保留 source reference / activity log。它说明 Agentic RAG 的价值不是名字，而是**用额外规划与多路检索换复杂问题的 evidence coverage**。

代价也必须回答：更多 LLM/retrieval 调用意味着 latency/cost 增加；错误 query planning 会放大偏差；如果允许循环检索，还需要 budget、stopping condition 和 eval。简单、单跳、查询模式稳定时固定 RAG 往往更便宜、更可预测。

## Vector DB 不能替代关系库

向量库擅长相似性检索；关系库擅长业务实体、事务、唯一约束、权限、版本、审计。典型组合：关系库保存 document/tenant/version/ACL/source-of-truth，向量索引保存 chunk embedding + metadata pointer。
## 高频面试题与答案骨架

**Q1：RAG 一次回答错误怎么排查？** 必须分层：数据源是否有答案 → parse/chunk 是否保留语义 → embedding/query 是否匹配 → top-k 是否召回 → metadata/ACL 是否过滤错 → rerank 是否把正确证据压下去 → final context 是否包含正确证据 → generation 是否仍幻觉。不能一句“模型不行”。

**Q2：Chunk size 怎么选？** 没有万能值。按语义边界、文档结构、查询粒度、上下文窗口和评测结果选；代码可按 symbol/AST，规范文档可按标题/段落。需要用 gold set 比较，而不是拍脑袋。

**Q3：为什么 hybrid retrieval？** Dense 擅长语义，sparse 擅长精确词项。Coding Agent 场景中函数名、错误码、配置项很重要，所以 hybrid 往往比纯 dense 更稳，但增加索引和融合复杂度。

**Q4：Rerank 的价值和成本？** 先用便宜 retriever 扩大召回，再用更强模型重排少量候选，提高 precision；代价是额外 latency/cost，因此需要控制 candidate size 并用 eval 证明收益。

**Q5：如何做多租户 RAG？** ACL 必须在 retrieval boundary 强制实施，不能只在 prompt 写“不要泄露”。优先用 tenant/project/ACL metadata pre-filter 或权限允许集合，再做向量检索；结果还要审计 source/version。

**Q6：RAG 和 fine-tuning 怎么选？** 需要动态外部知识、可更新、可追溯时优先 RAG；需要改变模型行为/风格/特定能力时才考虑 fine-tuning。两者可组合，不是互斥。

**Q7：固定 RAG 和 Agentic RAG 怎么选？** 单跳、查询模式稳定时优先固定链路；复杂多跳或需要根据中间证据继续找信息时再考虑 Agentic RAG。回答必须补上 query planning、并行子查询/多路检索、rerank、引用，以及 latency/cost/budget/stopping/eval，不要把“加 Agent”当升级理由。

## 最小评测指标

- Retrieval Recall@K：正确证据是否进入候选。
- Precision/Noise：候选中无关内容比例。
- Groundedness：回答是否被证据支持。
- Answer correctness：最终答案是否正确。
- Abstention：没有证据时能否拒答。
- Latency / token / cost：方案是否能上线。

## 故障题

1. 正确文档存在但从不被召回：优先查 chunk、query formulation、embedding、metadata filter。
2. 召回正确但回答仍错：查 context assembly、prompt、conflicting chunks、generation。
3. A 租户查到 B 租户文档：这是安全事故，不是“检索精度问题”；ACL 必须进入系统设计和测试。

## 面试系统设计题

设计“企业研发知识助手”：要求代码库 + 文档 + API 规范检索，多租户、版本更新、引用溯源。回答至少覆盖 ingestion、chunk strategy、hybrid retrieval、ACL、rerank、gold-set eval、删除/版本同步、fallback。
