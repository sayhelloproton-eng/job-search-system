# 05｜Context / State / Memory / Orchestration

## JD 为什么问

驿道、吉利、小红书、华为等岗位都把上下文、记忆、状态管理、任务编排放在核心能力。面试最容易暴露的问题是把“聊天记录”“Memory”“Workflow state”混成一件事。

## 三层必须分开

```text
Model Context
= 本次模型调用真正看到的输入

Runtime State
= 当前 run 做到哪一步、工具结果、审批、错误、retry 等执行事实

Long-term Memory
= 跨 run 仍需保留、未来可能再次使用的事实/偏好/经验
```

Context 有窗口和成本；State 要 durable；Memory 要有写入、更新、冲突、过期、删除策略。

## 最小状态机

```text
RECEIVED
  ↓
RETRIEVING
  ↓
PLANNING
  ↓
WAITING_APPROVAL
  ↓
EXECUTING
  ├──→ SUCCEEDED
  ├──→ FAILED
  └──→ CANCELLED
```

状态机的意义：让“系统现在到底在哪”变成显式事实，而不是依赖模型聊天历史猜测。

## Checkpoint / Resume

Checkpoint 保存可恢复的执行状态。恢复时不能把整个任务从头盲跑，尤其是已经执行过有副作用的步骤。要保存 step status、tool result/id、approval state、version，并保证可重放步骤和不可重放步骤边界清晰。

LangGraph 当前官方 persistence 也是以 checkpoint/thread 为核心，支持 HITL、memory、time travel、fault tolerance；失败后可以从成功 checkpoint 恢复，而不是全部重跑。
## HITL / Retry / Timeout / Cancel

Human-in-the-loop 不是“人工帮模型想”，而是在高风险或不确定动作前暂停 execution，让人 approve/edit/reject，再从原 state 恢复。当前 LangGraph 官方 HITL 也依赖 persistence/thread state 来 pause/resume。

Retry 必须回答两个问题：错误是否 retryable？重复执行是否安全？网络 timeout、429、临时 5xx 可能重试；权限拒绝、参数非法、业务冲突通常不应盲重试。

Cancel 需要定义语义：只取消未开始步骤，还是中断当前外部任务？已经产生的副作用是否需要补偿？

## Memory 分类

- Conversation/short-term：当前线程历史，通常受 context window 控制。
- Profile/fact memory：用户/项目稳定事实，需要 source、version、conflict resolution。
- Episodic memory：过去任务/经验，未来可被检索复用。
- Procedural knowledge：规则/流程更适合 Skill/Policy，不一定作为“Memory”。

## 高频面试题

**Q1：Context、State、Memory 区别？** Context 是给模型看的投影；State 是系统执行真相；Memory 是跨任务长期保留的信息。State/Memory 可用于构造 Context，但三者不能等同。

**Q2：Agent 中途挂了怎么恢复？** 从 durable checkpoint 读取 run/step/tool 状态，识别已完成和 pending；纯计算步骤可重放，有副作用步骤先做幂等/结果查询；恢复后继续下一安全节点。

**Q3：为什么不能把所有历史都塞 Context？** 成本和窗口有限、噪声增加、旧事实可能冲突、敏感数据暴露。需要 retrieval/summarization/selection，并保留真正 source-of-truth 在外部 state/memory store。

**Q4：什么时候必须 HITL？** 不可逆、高价值、外部影响大、权限敏感、模型置信不足或业务规则要求的动作，例如删除、支付、发布、发外部消息。

**Q5：Workflow 和 Agent 有什么区别？** Workflow 的路径大部分由代码预定义，Agent 把部分 next-step 决策交给模型。生产系统常混合：确定性的安全/交付流程用 workflow，开放性判断局部交给 Agent。

## 故障题

Agent 执行 `deploy` 后进程崩溃，DB 中只写了 EXECUTING。恢复时不能再次 deploy；先用 operation/idempotency id 查询部署平台结果，将 UNKNOWN 收敛成 SUCCEEDED/FAILED，再决定后续。

## 你的证据映射

DIRECT/TRANSFERABLE：project-context、Workflow、Plugin lifecycle/Gate 已体现 context 与确定性流程治理；但系统化 Memory/Checkpoint/Resume 仍是学习和实验项。
